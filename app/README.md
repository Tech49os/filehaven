# 文件管家 · 本地智能文件归档客户端

依据 `../本地智能文件归档客户端_需求方案_v0.3.md`、`../本地智能文件归档客户端_技术设计文档_v1.0.md`、
`../UI设计约束_v1.0.md` 实现的桌面客户端。

**技术栈**：Tauri 2 + Rust（后端） + Vue 3 + TypeScript + Vite（前端）

---

## 一、运行

### 用打包好的客户端

```
D:\filemanager\app\src-tauri\target\release\file-manager.exe
```

双击即可运行，无需安装依赖。

### 开发模式

```bash
cd app
npm install
npm run dev          # 浏览器调试（只有示例模式可完整跑）
npm run app:dev      # Tauri 开发模式，热更新 + 真实文件操作
```

### 构建

```bash
npm run build        # 仅前端 → dist/
npm run app:build    # 完整构建 exe + 安装包
```

> Windows 需要 Rust（msvc toolchain）+ MSVC Build Tools。本项目已在
> `rustc 1.100.0 / Visual Studio 2022 Build Tools` 环境下验证通过。

## 二、架构

```
┌──────────────────────────────────────────────┐
│  WebView2 (Vue 3 + Pinia + vue-router hash)  │
│   向导 6 步 · 主界面 5 页 · 13 个组件         │
└───────────────┬──────────────────────────────┘
                │ Tauri IPC（invoke / event）
┌───────────────▼──────────────────────────────┐
│  Rust 后端（src-tauri/src）                   │
│   scan.rs    递归扫描 + 系统目录黑名单         │
│   extract.rs Office/draw.io/纯文本 正文抽取    │
│   migrate.rs 三段式迁移 + 撤销                │
│   main.rs    命令注册 + 原生目录选择           │
└──────────────────────────────────────────────┘
```

Rust 侧零第三方运行时依赖（仅编译期 crate），exe 单文件 4.6 MB。

### Rust 命令（前端通过 `src/core/desktop.ts` 调用）

| 命令 | 作用 |
|---|---|
| `pick_directory` | 系统原生目录选择框 |
| `scan_directory` | 递归扫描 + 抽取正文，进度通过 `scan-progress` 事件推送 |
| `migrate_files` | 三段式迁移，进度通过 `migrate-progress` 事件推送 |
| `undo_migration` | 按批次从隔离区还原 |
| `prepare_archive_root` | 创建归档根与 `.filemanager` 结构 |
| `open_path` | 在资源管理器中打开 |
| `path_info` / `disk_free_gb` | 路径与磁盘信息 |
| `llm_request` | 代理本地大模型 HTTP 请求（绕开 WebView 的 CORS 限制） |

## 三、安全设计（这是产品的信任基础）

一次迁移，每个文件都走完三步，**任一步失败都保留原件**：

1. **复制**到目标目录 —— 同名自动加 `_1`、`_2`，**永不覆盖**
2. **校验** SHA-256 —— 与源不一致就删掉副本、报错、原件不动
3. **源文件移入隔离区** `<归档根>\.filemanager\trash\<批次号>\` —— **不是删除**

撤销时反向执行：隔离区 → 原位置（校验通过）→ 删除归档副本 → 清隔离区。

**系统目录强制黑名单**（不可由用户放开）：Windows、Program Files、ProgramData、
AppData、`$Recycle.Bin`、System Volume Information、node_modules、.git 等；
归档根自身也强制跳过，避免自我递归。

## 七、大模型增强（v0.2.0 已接入）

分类是**规则引擎 + 本地 Ollama** 的分工协作，不是单纯丢给模型：

```
扫描 → 规则引擎初判（毫秒级，450 文件 ≈ 10ms）
        │
        ├─ 高置信（文件名有项目专名，conf ≥ 0.9）→ 直接采用，不调模型
        │
        └─ 没把握（无工作域 / conf < 0.9）且**有正文**且**不是源码**
                ↓
           本地大模型逐份复核（约 3 秒/份，可中止）
                ↓
   ┌────────────┬──────────────┬─────────────┐
   │ 两路一致    │ 模型补盲      │ 两路分歧     │
   │ 置信度抬到  │ 规则判不出、  │ 保留规则结论  │
   │ 0.93 自动归档│ 模型读正文判出 │ 强制进待确认  │
   │            │ 0.76 待确认   │              │
   └────────────┴──────────────┴─────────────┘
```

一句话概括策略：**模型负责把「对的」确认下来，不负责把「错的」改掉。**
错标的代价（文件被静默塞进别人的项目）远高于多点一次确认。

### 为什么这样分工

依据 `../LLM评测报告.md`（91 份真实样本、三个模型、182 条原始输出）：

- **工作域**：模型更强（79.2% vs 规则 70.8%）→ 用模型补
- **文档类型**：规则更强（87.5% vs 79.2%）→ 规则优先
- **双路一致**：12/12 全对 → 可以直接给高置信
- **双路分歧**：实测里规则更可靠（演示集 4 处分歧规则全对）→ 不按模型改判，一律交人

### 三个关键实现细节

1. **结构化输出用 JSON Schema + enum 钉死**：模型只能从 9 个工作域 + 10 个类型里选，
   从解码层杜绝「技术方案」「智能工厂平台/钻采院项目」这类清单外发明。
2. **只输出 ws / dt 两个字段**：每多一个字段多约 10 token，7B 在 4060 上只有 ~7 token/s，
   两字段 3.8s、四字段 6.5s。模型自评的置信度本来就不可信（评测里 0 次说"不知道"）。
3. **请求走 Rust 而不是浏览器 fetch**：Windows 上 Tauri 页面 origin 是
   `http://tauri.localhost`，不在 Ollama 默认 CORS 白名单里，直连会 403。

### 相关文件

| 文件 | 作用 |
|---|---|
| `src/core/llm.ts` | Ollama 客户端（模型列表 / 预热 / 结构化分类 / 小并发） |
| `src/core/hybrid.ts` | 规则×模型融合与建树（纯函数 `fuseVerdict` 便于测试） |
| `src/core/classifier.ts` | 规则引擎；`buildTaxonomy` 被两条路径共用 |
| `test/hybrid-e2e.ts` | 混合管线端到端测试：`npx tsx test/hybrid-e2e.ts qwen2.5:7b` |
| `test/bench.json` · `test/eval.py` | 评测基准与评测脚本 |
| `src-tauri/src/main.rs::llm_request` | Rust 侧 HTTP 代理 |

诊断：`file-manager.exe --llmtest D:\out.json qwen2.5:7b` 可直接验证 Rust 能否连通 Ollama。

### 实测数据（本机 RTX 4060 Laptop 8GB）

| 模型 | 单份耗时 | 备注 |
|---|---|---|
| qwen2.5:7b | **3.0 ~ 3.3 s** | 默认，评测工作域 79.2% |
| qwen3.5:9b | 4.3 s | 支持看图，未参与本轮评测 |

并发实测无效：同一批 9 份文件，并发 1 和并发 4 都是 27 秒（Ollama 默认串行推理），
所以并发数留在 2 只是保守值，不要指望它提速。

真实桌面 453 份文件（其中 319 份有正文）跑一遍默认设置（smart + 上限 60 份）：

| 指标 | 结果 |
|---|---|
| 送模型 | 45 ~ 60 份（按置信度从低到高挑） |
| 耗时 | 155 ~ 190 秒 |
| 双路一致（抬到 93% 自动归档） | 28 ~ 30 份 |
| 模型补判（规则判不出，76% 待确认） | 6 份 |
| 双路分歧（66% 待确认，预填规则结论） | 6 份 |
| 待确认总数 | 280 → **262** |
| 判不出工作域 | 110 → **104** |

两个坑（都是真实语料上撞出来的）：

- **源码文件不能送模型**：`components.js`、`tickets.html` 会被读成「部门管理 · 单据表单」
  （看到 ticket 就想到工单），补判 12 份里 7 份是这种噪音，现在 `code` / `other` 直接跳过。
- **模型会把项目背景当归口**：正文反复出现「智能工厂平台」，它就把安全检查报告、费率清单、
  服务器配置清单全归到该项目。提示词加了第 5 条「项目名不是归口」后部分纠正，
  但仍会有分歧，所以分歧一律不采信模型、保留规则结论交人确认。

73 份演示样本（`induceHybrid` + smart 策略）：送模型 14 份 / 双路一致 8 / 分歧 3，
工作域 97%、类型 97%，总耗时 44 秒。

450 份真实桌面文件预估：需模型复核 190 份 ≈ **10 分钟**（界面有实时进度、可随时中止）。
