## 1. 系统总体架构

### 1.1 架构总览

系统采用 Tauri 2 的双进程模型，整体分为三层：**UI 层（WebView / Vue3）**、**核心服务层（Rust 主进程）**、**本地资源层（SQLite + 文件系统 + 内嵌模型）**。

```
┌─────────────────────────────────────────────────────────────┐
│                    UI 层 (WebView / Vue3)                     │
│   向导 7 步 │ 分类树 │ 待确认队列 │ 迁移预览 │ 搜索 │ 设置    │
└───────────────┬─────────────────────────────────────────────┘
                │  Tauri IPC (invoke 命令 / event 推送)
┌───────────────┴─────────────────────────────────────────────┐
│              核心服务层 (Rust 主进程 / Tauri Backend)         │
│  ┌─────────┬──────────┬──────────┬──────────┬────────────┐  │
│  │ Scanner │Extractor │AI Pipeline│Migrator │ Scheduler  │  │
│  │ 文件扫描│ 特征抽取 │ 推理管线  │安全迁移 │ 空闲调度    │  │
│  └────┬────┴────┬─────┴────┬─────┴────┬─────┴──────┬─────┘  │
│       │         │          │          │            │        │
│  ┌────┴─────────┴──────────┴──────────┴────────────┴─────┐  │
│  │              统一数据访问层 (Repository)               │  │
│  └────────────────────┬───────────────────────────────────┘  │
└───────────────────────┼─────────────────────────────────────┘
                        │
┌───────────────────────┴─────────────────────────────────────┐
│                   本地资源层                                   │
│   SQLite (索引/分类/迁移日志)   文件系统   内嵌模型文件        │
│   - files / categories          原始文件   - Qwen2.5-3B GGUF │
│   - FTS5 全文索引               归档根目录 - CLIP ViT-B/32   │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 Tauri 2 进程模型

Tauri 2 使用系统 WebView（Windows 上为 WebView2），不打包 Chromium，这是"运行时轻"的基石。

| 进程 | 职责 | 技术栈 | 资源特征 |
|---|---|---|---|
| **主进程 (Rust)** | 文件扫描、特征抽取、AI 推理、迁移、调度、数据库 | Rust + Tauri 2 | 空闲时 40–80MB；推理时按需增长 |
| **WebView 进程** | UI 渲染与交互 | Vue3 + 系统 WebView2 | 由系统管理，不打包 Chromium |

**AI 推理不另起 sidecar 进程，而在主进程内通过线程池执行**，理由：
- 避免 sidecar 进程间通信开销与进程管理复杂度；
- 用 Rust 的线程池（rayon / tokio spawn_blocking）即可精确控制并发与资源；
- 推理任务通过优先级线程 + 限速运行，不阻塞 UI 线程（Tauri command 在 async runtime 上执行）。

> 技术储备说明：若后续模型增大到需要独立进程隔离崩溃，可平滑切换为 Tauri sidecar 方案，接口不变。

## 2. 模块划分

### 2.1 模块清单与职责

| 模块 | 职责 | 关键输入 | 关键输出 |
|---|---|---|---|
| **scanner** 扫描器 | 全盘/增量扫描，黑名单过滤，断点续扫，文件元数据采集 | 扫描配置（根、黑名单） | 文件索引记录 |
| **extractor** 特征抽取器 | 从文件抽取文本、draw.io 节点、图片特征 | 文件路径 | text_content / drawio_nodes / image_embedding |
| **ai_pipeline** AI 推理管线 | 模型加载/释放、归纳分类、单文件分类、命名建议、置信度 | 特征向量 + 已有分类体系 | 分类、标签、命名、置信度 |
| **migrator** 安全迁移引擎 | 三段式迁移（复制→校验→回收）、冲突处理、撤销、磁盘预检 | 迁移计划 | 迁移结果、撤销记录 |
| **scheduler** 空闲调度器 | Windows 空闲检测、增量触发、资源限速、待确认队列管理 | 调度配置 | 整理任务触发与状态 |
| **repository** 数据访问层 | 所有 SQLite 读写、事务、FTS5 维护 | 业务对象 | 持久化结果 |
| **commands** 命令层 | Tauri command handler，前后端边界 | 前端 invoke | 序列化响应 |
| **ui** 前端 | 向导、主界面、交互 | 用户操作 | 渲染界面 |

### 2.2 模块依赖关系

```
ui ──invoke──> commands ──> repository ──> SQLite
                        ├──> scanner ──────────> repository
                        ├──> extractor ────────> repository
                        ├──> ai_pipeline ──────> repository (读特征/写分类)
                        ├──> migrator ─────────> repository + 文件系统
                        └──> scheduler ─┬─> scanner (增量)
                                        ├─> extractor
                                        ├─> ai_pipeline
                                        └─> migrator
```

关键原则：
- **repository 是唯一数据出口**，所有模块通过它读写 SQLite，禁止直连；
- **ai_pipeline 不直接操作文件系统**，只消费 extractor 产出的特征，输出分类建议；
- **migrator 是唯一允许移动/删除文件的模块**，且强制走三段式；
- **scheduler 是 scheduler/or/migrator 的编排者**，日常增量时按序调用 scanner→extractor→ai_pipeline→migrator。

## 3. 数据库设计

### 3.1 概览

- 引擎：SQLite（rusqlite bundled 模式，零外部依赖）；
- 数据库文件位置：`<归档根目录>/.filemanager/index.db`（与归档目录绑定，便于整体迁移）；
- 启用 WAL 模式提升并发读写；
- 全文检索使用 FTS5，中文分词先 simple tokenizer（按字切分，够用），后续可换 jieba。

### 3.2 表结构 DDL

```sql
-- 启用 WAL
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;

-- ============ 文件索引表 ============
CREATE TABLE files (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    path_hash       TEXT    NOT NULL UNIQUE,   -- 规范化路径 SHA256，增量去重

    normalized_path TEXT    NOT NULL,
    file_name       TEXT    NOT NULL,

    size_bytes      INTEGER NOT NULL,

CREATE INDEX idx_migrations_status ON migrations(status);

    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    type                TEXT    NOT NULL,      -- full | incremental

    blacklist_json      TEXT    NOT NULL,
    total_files         INTEGER NOT NULL DEFAULT 0,
    processed_files     INTEGER NOT NULL DEFAULT 0,
    last_processed_path TEXT,                  -- 断点续扫游标
    started_at          INTEGER NOT NULL,
    finished_at         INTEGER
);

-- ============ 待人工确认队列 ============
CREATE TABLE pending_queue (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id             INTEGER NOT NULL UNIQUE,
    reason              TEXT    NOT NULL,      -- low_confidence | drawio_parse_error | conflict | no_text
    suggested_category_id INTEGER,
    suggested_name      TEXT,
    confidence          REAL    NOT NULL DEFAULT 0,
    user_decision       TEXT    NOT NULL DEFAULT 'pending', -- pending|accepted|modified|rejected
    user_category_id    INTEGER,               -- 用户改后的分类
    user_name           TEXT,                  -- 用户改后的名
    created_at          INTEGER NOT NULL,
    resolved_at         INTEGER,
    FOREIGN KEY (file_id) REFERENCES files(id) ON DELETE CASCADE
);
CREATE INDEX idx_pending_decision ON pending_queue(user_decision);

-- ============ 配置表 (KV) ============
CREATE TABLE settings (
    key     TEXT PRIMARY KEY,
    value   TEXT NOT NULL                     -- JSON 序列化
);

-- ============ 审计日志 ============
CREATE TABLE audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    action      TEXT    NOT NULL,             -- scan_start|classify|migrate|undo|scheduler_trigger...
    detail      TEXT,                          -- JSON
    timestamp   INTEGER NOT NULL
);
CREATE INDEX idx_audit_time ON audit_log(timestamp);

-- ============ FTS5 全文索引（中文按字切分） ============
CREATE VIRTUAL TABLE files_fts USING fts5(
    file_name,
    text_content,
    drawio_nodes,
    image_caption,
    content='',
    tokenize='simple'                          -- 后续可替换为 jieba
);
-- 触发器保持 FTS 与 files/features 同步
CREATE TRIGGER files_fts_insert AFTER INSERT ON file_features BEGIN
    INSERT INTO files_fts(rowid, file_name, text_content, drawio_nodes, image_caption)
    SELECT f.file_name, NEW.text_content, NEW.drawio_nodes, NEW.image_caption
    FROM files f WHERE f.id = NEW.file_id;
END;
```

## 4. 核心子系统设计

### 4.1 文件扫描器 (scanner)

**职责**：遍历文件系统，过滤黑名单，采集元数据，支持断点续扫与增量。

```rust
// 核心接口（伪签名）
pub struct ScanConfig {
    pub scan_roots: Vec<PathBuf>,       // 用户选择的全盘根（各盘根）
    pub blacklist: Vec<String>,         // 系统目录黑名单（见第 10 节）
    pub archive_root: PathBuf,          // 归档根目录（排除扫描，防递归）
    pub max_file_size_mb: u64,          // 跳过超大文件（默认 2048）
    pub include_extensions: Option<Vec<String>>, // null=全部
}

pub struct ScanProgress {
    pub total: u64,
    pub processed: u64,
    pub current_path: String,
    pub found_new: u64,
    pub skipped: u64,
}

pub async fn run_scan(cfg: ScanConfig, task_id: i64, tx: EventSender) -> Result<ScanSummary>;
pub fn pause_scan(task_id: i64);
pub fn resume_scan(task_id: i64) -> Result<()>;
```

**设计要点**：
- **黑名单匹配**：路径规范化后做前缀匹配，强制排除（见 10.1）；
- **增量扫描**：对每个路径算 `path_hash = SHA256(规范化路径)`，查 `files` 表，不存在或 `mtime` 变化才处理；
- **断点续扫**：每处理 N 个文件（默认 500）将 `last_processed_path` 写入 `scan_tasks`，中断后从游标恢复；
- **并发控制**：用 `rayon` 线程池，默认 2–4 并发遍历，IO 密集型；
- **进度推送**：通过 Tauri event 实时推 `scan:progress`，前端进度条；
- **不卡机**：线程优先级设为低（Windows `SetThreadPriority`），扫描速率可限。

### 4.2 特征抽取器 (extractor)

**职责**：按扩展名路由到对应解析器，产出 `file_features` 记录。

| 扩展名 | 解析器 | 产出 |
|---|---|---|
| `.docx` | docx-rs | text_content（段落文本拼接） |
| `.xlsx` | calamine | text_content（单元格文本） |
| `.pdf` | pdf-extract | text_content |
| `.txt/.md/.log/.csv` | 直接读 | text_content |
| `.drawio/.xml`(drawio) | roxmltree XML | drawio_nodes（mxGraphModel 节点 userObject label） + text_content |
| `.pptx` | 解析 XML | text_content（slide 文本） |
| `.png/.jpg/.jpeg/.bmp/.webp` | CLIP | image_embedding + image_caption |
| 其他 | 跳过抽取 | 仅元数据 |

**draw.io 解析专项（★差异化）**：
```rust
pub fn parse_drawio(xml: &str) -> Result<DrawioFeature> {
    // 解析 <mxGraphModel> 下的 <UserObject label="..."> 或 <mxCell value="...">
    // 抽取所有 label/value 文本，去重，作为节点文字数组
    // 兜底：若 XML 结构异常，返回 parse_error，文件进待确认队列
}
```
- 节点文字数组用于：① AI 分类输入；② 全文索引（可搜图内文字）；③ 命名建议（取最高频主题词）。

**文本摘要截断**：`text_summary` 截断到 ≤2000 字（中文按字符），供 LLM 输入，避免超出上下文。

### 4.3 AI 推理管线 (ai_pipeline)（★核心）

这是产品差异化的技术核心，分两个阶段：**归纳（首次）** 和 **归类（增量）**。

#### 4.3.1 模型加载与释放

```rust
pub struct ModelManager {
    llm: Mutex<Option<LlamaModel>>,     // Qwen2.5-3B，按需 load/drop
    clip: OnceCell<ClipModel>,          // CLIP 常驻（小，350MB）
    thread_limit: usize,                // 推理线程数上限（默认 = 物理核/2，最少2）
}
impl ModelManager {
    pub async fn ensure_llm(&self) -> Result<&LlamaModel>;   // 懒加载
    pub fn release_llm(&self);                                // 用完释放，降内存
}
```

- LLM 空闲时不驻留（节省 ~2GB 内存），归纳/分类前 `ensure_llm`，批次完成后 `release_llm`；
- CLIP 常驻（350MB 可接受），图片特征随时可算；
- 推理线程数可配，默认物理核数的一半，避免占满 CPU。

#### 4.3.2 阶段一：归纳分类体系（首次，★差异化）

用户没有预定义分类，系统先聚类再让 AI 命名：

```
步骤 1: 特征聚类
  - 对所有已抽取特征的文件，用 TF-IDF + 层次聚类（纯 Rust，不依赖 LLM）
    或用 CLIP 向量（图片）+ 文本 embedding 聚类
  - 产出 N 个簇（自动决定簇数，用轮廓系数辅助）

步骤 2: LLM 为每个簇命名
  - Prompt: "以下是同一类文件的标题与摘要样本：[样本]。请用中文给出
    一个简洁的分类名（≤6字）和一句话描述。只返回 JSON。"
  - 每簇采样 10–20 个代表性文件送入，控制 token
  - 产出: { name, description } → 写入 categories（is_from_ai=1）

步骤 3: 组织成树
  - 对命名后的分类做二级归纳：把相似顶层分类合并
    （如"支付方案"+"订单方案"→ 父节点"技术方案"）
  - 形成 2 层分类树展示给用户

步骤 4: 为每个文件打分类 + 标签 + 命名建议 + 置信度
  - 用 LLM zero-shot 对每个文件特征做分类（约束在已归纳的 taxonomy 内）
  - 命名建议: "根据内容生成归档文件名，格式 2026-11_<主题>_<类型>_v1"
  - 置信度 < 0.7 → 进 pending_queue，不硬猜
```

**约束输出防漂移**（参考 AI File Sorter）：
- 归类时 Prompt 中**枚举当前 taxonomy 全部分类名**，要求 LLM 只能从中选，避免每次发明新分类；
- 用 JSON Schema / function-calling 式约束输出格式。

#### 4.3.3 阶段二：增量归类（日常）

```
对新增/变更文件：
  1. extractor 抽取特征
  2. CLIP 算图片 embedding（若图片）
  3. LLM 在已固化 taxonomy 内 zero-shot 分类
  4. 置信度分流：≥0.7 自动迁移；<0.7 进待确认队列
```

#### 4.3.4 推理资源控制

- 批次推理：单文件逐个调 LLM 太慢，**批量拼 prompt**（多个文件摘要放一个 prompt，一次推理多个结果）；
- 推理在 `tokio::spawn_blocking` + 低优先级线程执行，不阻塞 UI；
- 可设"推理 CPU 上限百分比"，超过则暂停本批。

### 4.4 安全迁移引擎 (migrator)（★信任基石）

三段式，对应 v0.3 第 6 节，绝不直删、绝不覆盖：

```rust
pub struct MigrationPlan {
    pub file_id: i64,
    pub source: PathBuf,
    pub target_dir: PathBuf,   // <归档根>/<分类路径>
    pub new_name: String,
}

pub async fn execute_migration(plans: Vec<MigrationPlan>, batch_id: &str, tx: EventSender)
    -> Result<MigrationReport>;

// 三段式（单文件事务）
fn migrate_one(plan: &MigrationPlan) -> Result<MigrationRecord> {
    // ① 复制：只读复制到目标，同名加序号 _1 _2，绝不覆盖
    let target = resolve_conflict(plan);  // 若存在则加序号
    fs::copy(&plan.source, &target)?;

    // ② 校验：大小 + SHA256 比对，一致才继续
    if !verify_hash(&plan.source, &target)? {
        fs::remove_file(&target)?;        // 删掉错误的副本，保留原件
        return Err(HashMismatch);
    }

    // ③ 回收：校验通过后，源文件送系统回收站（可恢复）
    send_to_recycle_bin(&plan.source)?;   // Windows SHFileOperation FO_DELETE + FOF_ALLOWUNDO

    Ok(MigrationRecord { source, target, status: "recycled", .. })
}
```

**冲突处理**：
- 目标已存在同名 → 加序号 `_1`、`_2`，永不覆盖；
- 源与目标实为同一文件（content_hash 相同）→ 标记重复，源直接回收，不重复复制。

**撤销引擎**：
```rust
pub async fn undo_batch(batch_id: &str) -> Result<()> {
    // 读取 migrations 表该 batch 全部记录
    // 对每条 status=recycled 的记录：
    //   1. 从回收站还原源文件（或从 target 复制回 source）
    //   2. 删除 target 副本
    //   3. 标记 status=reverted
    // 回收站还原失败 → 从 target 反向复制回 source（target 是完整副本）
}
```

**磁盘预检**：执行前计算总复制体积，与目标盘剩余空间比对，不足则报错并提示。

### 4.5 空闲调度器 (scheduler)（★差异化）

Windows 上成品的定时整理能力缺失，这是差异化点之一。

```rust
pub struct SchedulerConfig {
    pub enabled: bool,
    pub idle_threshold_sec: u64,     // 空闲多久才触发（默认 600 = 10分钟）
    pub require_power: bool,         // 需接电源（默认 true）
    pub allowed_hours: Option<(u8,u8)>, // 允许时段，None=全天
    pub cpu_limit_percent: u8,       // CPU 上限（默认 30）
    pub check_interval_sec: u64,     // 空闲检测间隔（默认 60）
}
```

**空闲检测（Windows API）**：
```rust
// windows-sys: GetLastInputInfo() 获取上次输入时间
// 空闲时间 = GetTickCount() - lastInputInfo.dwTime
fn get_idle_seconds() -> u64;
// 另查电源状态: GetSystemPowerStatus() 判断 ACLineStatus
```

**增量整理流程（触发后）**：
```
1. scheduler 检测到空闲达标 → emit scheduler:idle_triggered
2. scanner.run_scan(incremental)  找新文件
3. extractor 抽取新文件特征
4. ai_pipeline 在已固化 taxonomy 内分类
5. 置信度 ≥0.7 → migrator 安全迁移；<0.7 → 进 pending_queue
6. 全程监控 CPU，超 cpu_limit 暂停，降后再续
7. 完成 → emit scheduler:done {整理N个，待确认M个}
```

**资源保护**：
- 推理线程数 = min(2, 物理核/4)；
- 每处理 50 个文件检查一次 CPU 占用，超标则 sleep；
- 前台有输入活动（非空闲）立即优雅暂停当前批次，记录断点。

### 4.6 索引与检索 (search)

- 全文检索走 FTS5，索引 file_name + text_content + drawio_nodes + image_caption；
- 支持过滤：分类、标签、扩展名、时间范围、置信度；
- draw.io 图内文字可搜（差异化）；
- 中文分词 MVP 用 simple（按字），V1 可换 jieba 提升召回。

### 7.2 日常增量整理时序

```
scheduler(空闲检测)
  │ idle 达标
  ├─> scanner.incremental_scan  ──> repository(找新文件)
  ├─> extractor(抽取新文件特征)──> repository
  ├─> ai_pipeline.classify(在已固化 taxonomy 内, 批量)
  │      ├─ confidence≥0.7 ──> migrator(三段式) ──> repository
  │      └─ confidence<0.7  ──> pending_queue
  ├─ 全程 CPU 监控，超限暂停
  └─ emit scheduler:done { migrated: N, pending: M }
```

### 7.3 撤销时序

```
用户点撤销 batch
  ─> migrator.undo_batch(batch_id)
       ─> 读 migrations 表该 batch 全部 status=recycled 记录
       ─> 对每条：从回收站还原源文件（失败则从 target 反向复制回 source）
       ─> 删除 target 副本
       ─> 标记 status=reverted
       ─> 更新 files.status 回 confirmed
  ─> 返回撤销报告
```

## 10. 安全设计

### 10.1 系统目录黑名单（强制排除）

扫描时路径规范化（转小写、去 `\\` 为 `\`、去相对段）后做前缀匹配，以下默认强制排除：

```
C:\Windows
C:\Program Files
C:\Program Files (x86)
C:\ProgramData
C:\Users\<user>\AppData
C:\Users\<user>\AppData\Local
C:\Users\<user>\AppData\Roaming
C:\Users\<user>\AppData\LocalLow
C:\$Recycle.Bin
C:\System Volume Information
C:\pagefile.sys / hiberfil.sys / swapfile.sys
<任意盘>:\WindowsApps
<归档根目录>             # 防递归
<安装目录>               # 程序自身
```

用户可在设置中**增加**排除项，但**不能删除**系统级强制项（UI 置灰）。

### 10.2 归档根目录合法性校验

`init_validate_root` 规则：
1. 不能是系统盘根（`C:\`）；
2. 不能在黑名单目录内；
3. 不能在被扫描范围内（防递归，扫描时自动排除）；
4. 所在盘剩余空间需 > 估算待整理体积（可放宽，仅警告）；
5. 路径可写、可创建子目录。

### 10.3 文件操作安全准则

- **唯一可写模块**：migrator 是唯一允许复制/删除（回收）文件的模块；
- **永不覆盖**：目标同名加序号；
- **永不直删**：源文件只送回收站（`SHFileOperation` + `FOF_ALLOWUNDO`）；
- **逐文件事务**：复制-校验-回收是一个事务，任一步失败都回滚到安全状态（保留原件）；
- **全程可撤销**：migrations 表记录所有操作，batch 级一键回滚。

## 11. 性能与资源控制设计

对应 NFR-1/2/3 与"运行时轻"核心约束。

| 手段 | 实现 | 效果 |
|---|---|---|
| 模型按需加载 | LLM 空闲释放，用时加载 | 空闲内存降 ~2GB |
| CLIP 常驻 | 仅 350MB（量化后 ~110MB） | 图片随时可算 |
| 推理限速 | 线程数 = 物理核/2，低优先级 | 不抢占前台 |
| 批量推理 | 多文件拼一个 prompt | 减少 LLM 调用次数 |
| 增量扫描 | path_hash + mtime 判变 | 二次扫描分钟级 |
| 断点续扫 | last_processed_path 游标 | 中断可恢复 |
| 空闲触发 | GetLastInputInfo + 电源 | 后台不打扰 |
| CPU 监控 | 每 50 文件检查占用，超限暂停 | 资源可限 |
| FTS5 索引 | 增量触发器维护 | 检索毫秒级 |

**目标指标**（对应 v0.3 G-2/G-3/G-5）：
- 空闲内存 ≤ 150MB（模型未加载时）；
- 推理峰值可控（线程+限速）；
- 百万级文件增量扫描 ≤ 分钟级（SSD，二次运行）；
- 后台整理前台无感。

## 12. 错误处理与日志

- 统一错误类型 `AppError`（enum），实现 `Into<String>` 供 command 返回；
- 文件级错误不中断批次：单文件失败记录 `files.status='error'` + `error_message`，继续下一个；
- 日志：`tracing` crate，分级（INFO/WARN/ERROR），输出到 `.filemanager/logs/app-YYYY-MM-DD.log`，滚动；
- 关键操作写 `audit_log` 表（scan_start/migrate/undo/scheduler_trigger）；
- 迁移失败清单可导出，供用户排查。
