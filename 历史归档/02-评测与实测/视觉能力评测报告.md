# 视觉能力评测：qwen3.5:4b 的图片与 PDF 识别

> 日期：2026-11-17
> 缘起：用户问「3.5 在图片识别、PDF 内容识别上会不会比 3 和 2.7 更好」
> 结论先行：**图片识别是「有 vs 无」——只有 qwen3.5 有 vision，能补上 4 张图里 1 张文件名无信息的短板；PDF 内容识别 Vision 目前不占优，且更该先做文本层解析（管线问题，非模型问题）。**

---

## 一、关键前提：只有 qwen3.5 支持视觉

Ollama 能力清单（`GET /api/tags`）：

| 模型 | vision | thinking | 能看图？ |
|---|---|---|---|
| qwen2.5:7b | ✗ | ✗ | 不能 |
| qwen3:4b-q4_K_M | ✗ | ✓ | 不能 |
| **qwen3.5:4b** | **✓** | ✓ | **能** |

所以「图片识别」不是三个模型比高低，而是 **3.5 独有**。旧的 `eval.py` 只喂文件名+抽取的文本，图片/扫描件 PDF 的正文抽取返回空——三个模型都在盲猜，3.5 的视觉能力此前完全没用上。

---

## 二、图片识别实测（4 张真实图）

方法：同一张图跑两遍——A 仅文件名（复现旧做法），B 文件名+图片（`images` 字段传 base64）。真值由我人工看图判定，均属「智能工厂平台」。脚本 `app/test/vision-test.py`，数据 `vision-result.json`。

| 图片 | 真实内容 | A 仅文件名 | B 看图 | 视觉是否有益 |
|---|---|---|---|---|
| `20260917-185927.jpg`（时间戳名） | 智能工厂智匠智能体海报 | ✗ 说不知道 | ✓ 智能工厂平台 | **✓ 关键补救** |
| `cd847e97...jpeg`（哈希名） | 智能问数机器人 | ✗ 说不知道 | ✗ 知识沉淀 | ✗ 看图也错 |
| `苹果风格后台.jpg`（误导名） | 海油智能体平台后台 | ✓ 智能工厂平台 | ✓ 智能工厂平台 | 持平 |
| `海油发展智能工厂系统应用图标生成.png` | 系统图标 | ✓ 智能工厂平台 | ✓ 智能工厂平台 | 持平 |

- **A 正确 2/4，B 正确 3/4。** 视觉的唯一净收益是那张纯时间戳命名的海报——文件名零信息，看图后正确归类。
- 哈希名那张（9KB 小图）看图后判成「知识沉淀」，是**误判**：画面是通用机器人+看板，模型没认出 CNOOC 上下文。
- **诚实度反而更好**：A 模式两张无信息文件名，模型正确地说了「不知道」；这是对的行为（符合"低置信不硬猜"）。B 模式硬性给了答案，其中一个还是错的。

**结论：图片识别上 3.5 确实比另两个强（它们根本看不了），但净收益有限——4 张里只多救回 1 张，且有 1 张引入新错误。**

### 踩坑（写代码必读）
- **图片会编码成大量 vision token，`num_ctx=4096` 会直接 400**（实测单图 4329 token 超限）。必须 `num_ctx≥8192`。
- 模型输出可能套 ```json 代码块，解析要用正则抠 `{...}`，不能直接 `json.loads` 整体。

## 三、PDF 内容识别实测（6 份真实 PDF）

先厘清：PDF 有两种——**有文本层**（可用 pymupdf 直接抽字）和**扫描件/图片型**（没有文字，必须 OCR 或视觉）。探测发现样本里两种都有：

| PDF | 类型 | 文本层字数 |
|---|---|---|
| 合同签字版.pdf | 扫描件 | 0 |
| GB_T 22111-2008_895.pdf | 扫描件 | 0 |
| 数智化提升行动方案.pdf | 扫描件 | 0 |
| 关于成立数字化运营中心的通知.pdf | 有文本层 | 867 |
| 智能工厂人员安排.pdf | 有文本层 | 1235 |
| 质量之星申报.pdf | 有文本层 | 1934 |

三路对比：

| 路径 | 做法 | 有真值 2 份正确率 |
|---|---|---|
| A | 仅文件名 → 7b | **2/2** |
| B | 文本层抽字 → 7b | 1/2 |
| C | 首页渲染图 → 3.5 vision | 1/2 |

**关键发现（和预期相反）：**

1. **文本层解析（B）没赢过文件名（A）**，在有真值的 2 份上反而更差。原因不是文本没用，而是：
   - `合同签字版.pdf` 是扫描件，B 无文本可用（跳过）——这类只有 A 和 C 能比。
   - `智能工厂人员安排.pdf`：B/文件名都判对 ws，但 B 把 dt 从"空"补成了"方案设计"，未必更好。

2. **Vision（C）在 `合同签字版.pdf` 判成「油化厂项目」而非真值「商务采购」**——但这暴露的是**真值标注错误**：PDF 首页白纸黑字写着"油田化工智能工厂数字化系统深化建设项目服务合同"，按项目归属就该是油化厂项目。视觉如实读到了内容，比只看文件名更接近文件真实内容。**这份的 ground truth 需要修正**（列入待裁决清单）。

3. **扫瞄件 PDF（无文本层）才是 vision 的真正用武之地**：合同签字版、GB_T 国标、数智化方案这 3 份，文本层都是 0，文件名以外唯一能读内容的方式就是看图/OCR。C 在这 3 份上给出了基于真实内容的判断。

4. **文本层优先于视觉**：对有文本层的 PDF（通知、人员安排、质量之星），pymupdf 抽字又快又准（0 成本），没必要渲染成图再让模型看——视觉会引入"看错字/看错重点"的风险，且慢得多（14s vs 3s）。

## 四、综合裁决

| 场景 | 推荐 | 理由 |
|---|---|---|
| 图片分类 | **qwen3.5 vision 值得开** | 唯一能读图的模型；时间戳/哈希名文件靠它多救回 1/4，代价是 1 张误判 |
| 有文本层 PDF | **先做 pymupdf 文本层解析**，再喂文本模型 | 快、准、零成本；视觉无优势 |
| 扫描件 PDF | **vision 或 OCR**（当前只能靠 vision） | 文本层为空，文件名不可靠时唯一的内容来源 |
| 工作域/类型主分类 | 维持原方案（ws=7b / dt=规则） | 见 `LLM评测报告.md` 第九节 |

**落地建议（暂不实施，等用户点头）：**
1. 正文抽取管线加 PDF 分支：pymupdf 先抽文本层，`len(text)<阈值` 判定为扫描件 → 标记 `needs_vision`。
2. `needs_vision` 的文件（图片 + 扫描件 PDF）才调用 qwen3.5 vision，其余走文本快路径。
3. 视觉结果置信度仍不可全信——哈希名小图会误判，建议视觉结果与规则分歧时进人工队列。
4. **环境坑**：项目主 Python 是 3.13（装不了 pymupdf），PDF 库装在 `C:/Python314/python.exe`（3.14）。要落地需统一 Python 版本，或把 PDF 抽取做成独立进程。
