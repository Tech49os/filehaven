# 同一文件多版本处理方案 v1.0

> 2026-11-18 定稿。起因：用户实测后提出「针对同一文件不同版本这种情况需要设计个好点的方案」。
> 本文记录口径、策略、实测数据和边界，改代码前先读这一页。

## 一、问题有多大（455 份真实文件实测）

| 现象 | 规模 |
|---|---|
| 版本族 | **47 族 / 127 份（27.9%）** |
| 最大一族 | 7 个版本（`“智”造领航逐浪数字蓝海-集团` V1.1/V1.2/V1.3/V2.0/无版本号，每个 78–110MB） |
| 同尺寸可疑副本 | 13 组 / 26 份 |
| 会因为规范化改名 | 83 份 |

三个真问题：

1. **目录里平铺 6 个近似文件名**，用户打开归档目录还是不知道该用哪份。
2. **涌现统计被版本放大**：`df` 数的是「出现在多少份文件里」，同一份 PPT 的 7 个版本贡献 7 次。
   实测 `海油发展智能工厂` 因此从 10 份虚高到 51 份，直接把「给这个 PPT 建个类目」顶到第一名。
3. **字节完全相同的副本**白占空间，且在列表里和真版本长得一样。

## 二、口径：什么算「同一份文档的不同版本」

用**文件名归一化**判，不用哈希——同一文档的不同版本内容必然不同，哈希反而分不出来。
哈希只用来判「字节完全相同的副本」。

归一化规则（`app/src/core/version.ts` 的 `parseName`）：

| 痕迹 | 例子 | 处理 |
|---|---|---|
| 版本号 | `V1` `v1.2` `V2.0版本` | 剥出来，规范化成 `v1.2` |
| 中文版次 | `第3版` | 剥出来 |
| 收尾词 | `终版` `定稿` `初版` `草稿` `最新版` | 剥出来（强标记，随便剥） |
| 收尾弱标记 | `_修改` `_修订` `_完` | **必须前面有分隔符才剥**——`ppt修改.pptx` 里的「修改」是动词 |
| 重复下载 | `(1)` `(2)` | 剥出来，序号 = n+1（原件算第 1 份） |
| 前缀副本 | `副本xxx` `copy of xxx` | 纯噪音，剥掉但不记痕迹 |
| 日期 | `-20240315` `2026.8.4` | **只在算「是不是同一份」时忽略，展示和改名都留在原位** |

**两条不能碰的红线**（都有真实文件逼出来的教训）：

- 日期不是版本号。`人工智能推进会-生产智能化项目组-2026.8.4.pptx` 里 2026.8.4 是**会议日期**，
  改名成 `… (2026-08-04)` 就变成「这文件有多个日期版本」的意思了 → 保留原位。
  同理 `2024年度总结` 和 `2023年度总结` 绝不能并成一族（只在**结尾**认日期，且不进 key 之外的展示名）。
- 同主名不同扩展不能一律并族。`work-item-detail.html/.js/.css` 是三个不同文件，不是一份文档的三种格式。
  只有同扩展、或同为「文档 / 表格 / 幻灯 / PDF」时才并。

## 三、策略（用户 2026-11-18 拍板）

| 决策点 | 用户选择 |
|---|---|
| 落盘 | **全部版本都归档，一份不丢** |
| 命名 | **迁移过程中统一规范化** |
| 展示 | **同一族只显示一行，点击展开** |
| 字节重复 | **全部归档，只在预览里标注** |
| 默认动作 | **自动执行，预览页可逐个改** |

### 3.1 命名规范化（落盘）

`familyRenames()` 只对「族内 ≥2 份」的文件生效，单份文件一律不动：

```
技术方案V1.docx   + 技术方案v2.1.docx   →  技术方案 (v1).docx   /  技术方案 (v2.1).docx
ppt修改.pptx ×2（同名不同内容）        →  ppt修改.pptx         /  ppt修改 (副本2).pptx
汇报.pptx + 汇报(1).pptx + 汇报(2).pptx →  汇报.pptx           /  汇报 (副本2).pptx / 汇报 (副本3).pptx
技术方案.docx + 技术方案.pdf            →  都不改名（扩展不同不会撞名）
```

规则细节：

- 没有痕迹的那份保留原名（用户对它的记忆最深）
- 撞名时补 `(副本N)`，N 从mtime 次新的那份开始数；已经是 `(副本N)` 的就往上顶，不叠成 `(副本2) (副本2)`
- 版本族**只在同一个目标目录内成立**：A 事项的「方案V1」和 B 事项的「方案V2」互不相干
- 用 AI 建议名的文件不参与改名（名字是人定的）
- 待确认 / 未归类的文件不改名（本来就不迁移）

### 3.2 展示（确认页 + 迁移预览）

- 确认页右清单：`▸ 技术方案  3 个版本  最新 3.0MB · 05-01`，点开逐版列出原名/大小/时间/最新或旧版
- 迁移预览：同族折成一行，点开是每个版本各自的 `源名 → 目标名`
- 两处都不改行为，只改看法；族计数在预览页统计条上（`版本族 N 组`）
- 内容完全相同的副本在行上标「与另 N 份内容相同」，**不删不跳**

### 3.3 统计去重（算法层，收益最大）

`latestOnly()`：算候选词 `df` 时，每个版本族只留最新那份。

实测（455 份，缓存好的「谁」判定，不重调模型）：

| | 事项 | 已归类 | 未归类 |
|---|---|---|---|
| 现状（所有版本都数） | 45 | 304 | 151（33.2%） |
| **按族去重** | 47 | **318** | **137（30.1%）** |

代价：会多冒出几个碎片类（`平台技术室`、`发展智能工厂系统`），这些和之前已知的碎片类一起，
仍需人工在确认页删掉。**净收益是多了 14 份归类、少了 14 份未归类。**

### 3.4 字节重复：真的算哈希，但只算该算的

扫描后按大小分组，**只有「同尺寸且 ≥2 份」的文件**才送 `hash_files`（Rust 命令）。
真实 455 份里只涉及 26 份，毫秒级；全盘哈希要读几十 GB，不做。

## 四、不做什么（防止以后被"优化"回去）

| 不做 | 原因 |
|---|---|
| 删除旧版本 | 用户明确「全部归档」；旧版本也是资料，删了找不回来 |
| 用内容相似度判断版本 | 需要读全文+比对，455 份要跑很久，且 pptx/docx 二进制差异巨大 |
| 自动合并成一族就合并文件 | 折叠只是显示层，落盘永远一份文件一条记录 |
| 把日期当版本号 | 见二节红线 |
| 全盘哈希 | 性价比为零 |

## 六、验证结论

- 测试 222 全过，typecheck 干净
- 迁移完整性：455/455 覆盖、目标路径 0 重复、0 同名冲突
