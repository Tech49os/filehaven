# BUG-007 修复说明：整理台删除改为隔离区可撤销（红→绿）

## 1. 根因

整理台从来没有「删除」能力：

- **前端**：`Workspace.vue` / `FileCard.vue` 没有删除按钮；`core/keys.ts` 没有 Delete 键位；
  `core/ipc.ts` 没有删除命令封装。
- **后端**：46 个 Tauri 命令里没有删除命令，状态机 8 态里没有 `trashed`；
  `drop_file` 只是 `parked → skipped` 的状态流转，磁盘文件原封不动。
- **安全缺口**：如果按字面实现「删除」，最直接的做法是调用 Windows 回收站 API 或
  `fs::remove_file` —— 前者把用户文件交给系统、不可审计，后者是不可逆的数据丢失。
  所以本 bug 的重点不是「加一个删除按钮」，而是**把删除重新定义为移入隔离区**。

## 2. 安全模型（最高优先级铁律的落地）

```
源区文件  --move_file-->  <归档根>/.filebutler/quarantine/<批次id>/<源区相对路径>
   ^                                      |
   |-------------- undo_trash ------------|
```

| 铁律 | 落地方式 |
|---|---|
| 永不永久删除 | 新增代码零 `fs::remove_file`（对源文件）；只复用 `migrate::move_file`（同盘 rename / 跨盘 copy+校验+清源 的既有例外）。 |
| 不碰 Windows 回收站 | 未引入 `SHFileOperation` 或任何回收站 API；隔离区是应用自管的、可审计的目录。 |
| 目标路径沿用既有布局 | `plan::quarantine_path` 一处定义；`plan::unique_name` 撞名错开 `_2`，复制/移动前检测、`move_file` 也不覆盖已有文件。 |
| 哈希闸门 | 搬前 `sha256_of(src)`，搬后再 `sha256_of(dst)`；不一致则把原件搬回原处，不改状态、不留批次。跨盘分支 `move_file` 内部还有一次校验。 |
| 同事务语义 | `conn.transaction()` 内：预分配批次 id → 磁盘搬运+校验 → `migration_items` + `prev_status` + `status=trashed` + `finish_migration`。任一步 `Err` 直接退出，事务回滚，不留「库里有记录、文件没动」的幽灵批次。 |
| 撤销的硬闸 | 复用 `migrate::undo_one`：隔离区哈希必须与台账一致（篡改则拒），原路径已有同名则拒（不覆盖）。任一不过：原文件不动、状态仍 `trashed`、批次不标 `undone`、错误原因直达前端。 |
| 状态机不旁路 | `index::mark_trashed` / `restore_trashed` 是 trashed 写入的唯一入口，内部查 `ALLOWED`；仅 `pending_confirm/confirmed/parked → trashed`，撤销只回删除前状态。 |
| 不被通用 undo 误伤 | `migration::undo` 按 kind 拒绝 `trash`（同 BUG-003/006 的防护），提示走整理台的 `undo_trash`，避免台账被错标 `undone` 后专用入口失效。 |

## 4. 关键决策

1. **批次 id 与事务的顺序**：隔离区路径含 `<批次id>`，必须先拿到 id 才能算路径。做法是在
   `conn.transaction()` 内先 `insert_migration_with_kind(kind='trash')` 预分配 id，再做磁盘与台账操作；
   任何错误直接返回让事务回滚。这样既满足「沿用既有路径布局」，又满足「失败不留幽灵批次」。
2. **源文件的离开方式**：没有独立「复制→删源」步骤，而是复用 `migrate::move_file`：
   同盘 `rename` 是原子操作（不可能出现一半的副本），跨盘分支内部就是「复制 → SHA-256 校验 →
   成功后才清源」。移动完成后再验一次哈希作为兜底，不一致就把原件搬回原处。
3. **prev_status 存在哪里**：放在 `files` 表的新列（幂等补列），而不是塞进 `migration_items` 的
   复用列。撤销时 `strip_prefix(quarantine/<批次id>)` 从台账 dst 反推相对路径，因此撞名 `_2`
   也能准确找回；同时保留「从源区根目录重算」的兜底路径。
4. **Ctrl+Z 不新增键位**：复用既有 `undo` 命令，但 store 内优先消费 `trashUndo`，因此对用户仍是
   「Ctrl+Z 撤销刚才的删除」，代码上两条路各自调用正确的后端命令。
5. **不动 `drop_file`**：待定区 `parked → skipped` 语义完全保留；已归档文件由状态闸门和
   `archived_path` 双重拒绝，不在本 bug 范围。

## 6. 边界与遗留风险

- **不做「清空隔离区」**（另案）：隔离区文件会一直保留，直到用户按批次撤销或将来有清理功能。
- **已归档文件不可删**：`migrated` 状态与 `archived_path` 都被显式拒绝；会影响归档树与目录计数，另案处理。
- **极端时序**：若在 `tx.commit()` 失败的瞬间进程崩溃，可能出现「文件已进隔离区但没有台账」的孤儿副本；
  概率极低，且**绝不会永久丢失数据**（文件在隔离区里，可人工找回或后续做孤儿回收）。
- **跨盘回滚**：搬后哈希不一致时尽力把原件搬回；若原位置同时被用户新建同名文件占用，回滚会失败，
  此时原件仍在隔离区且不会丢，错误会明确报出，需人工处理。
- **`trash_file` 是单文件批次**：一份删除一个 `migrations` 行（kind=trash），便于逐份撤销与审计；
  不批量合并，避免一份失败拖累整批。
