## 核查「9b 在 8GB 显存处理 5000 字 prompt 直接失败」——原结论不成立

用真实数据复现（`app/test/stress-merge.ts`，走真实 `buildMergePrompt` + `candidates-real.json` 前 40 条
= 5039 字 / 3179 token，与出事的那个 prompt 同量级）：

| 条件 | 结果 |
|---|---|
| 9b, num_ctx 4096 | **152.9s 正常返回**，done_reason=stop，16 组合法 JSON |
| 9b, num_ctx 16384 | 148.7s，17 组，5.6 tok/s |
| 4b, num_ctx 8192 | 138.5s，8.3 tok/s 但输出 1062 token（比 9b 多 45%），墙钟一样；JSON 缺右括号解析失败 |

**证据（Ollama server.log 23:14:31 那次）**：prompt_eval 4348ms / 3177 token = **730 tok/s，prefill 4.4 秒**；
之后 eval 919 token @ 4.97 tok/s 跑了 185 秒 → `stop processing: n_tokens=4095, truncated=1`。
`/api/ps` 实测 size=size_vram=5.22GB，33/33 层全在 GPU，运行时余 1.6GB —— **没有 offload、没有 OOM、没有 CUDA 报错**。

所以「显存/prefill 撑不住」是错的。真实原因两层：
1. num_ctx 4096 时 3179 token 的 prompt 只剩 ~900 token 输出余量，模型写不完就撞上限被截断（truncated=1），拿到的不是有效答案；
2. 4.97 tok/s × 900 token ≈ 185s，超了客户端超时 → 表现为「199 秒断连」。`llm.ts` / Rust 侧默认 **60s**，更长必须显式传 `timeoutMs`。

**因此正确表述**：单次 40 候选归并约 **150 秒，可行但慢**；瓶颈是生成吞吐（~5 tok/s），不是显存。
179 个候选分 5 块 = 12 分钟，那才叫不可行。要提速只有三条：压输出 token（紧凑 JSON）、减候选数、
换 4b 也没用（输出更啰嗦，墙钟相等）。

## 附带发现：merge 的 rejected 是空格问题，不是幻觉
9b 输出 `AI 大赛`（带空格），候选池是 `AI大赛`，`parseMergeResult` 的 `pool.has()` 直接判 rejected。
两次跑各 8 个 rejected 多半是这类空格/大小写差异，归一化后覆盖率比 25/40 高。这个坑会误判模型质量。

## NPU 能否与 4060 叠加加速 —— 不能

本机确为 Intel Core Ultra 9 185H（Meteor Lake）+ Intel AI Boost NPU（PCI VEN_8086&DEV_7D1D，11 TOPS INT8），
内存 2×16GB DDR5-5600（89.6 GB/s），4060 Laptop 8GB（272 GB/s）。
1. Ollama 0.40.16 自带的 lib/ollama 只有 `cuda_v12`/`cuda_v13`/`rocm_v7_1`/`vulkan` + `ggml-cpu-*`，
   **无任何 openvino/NPU 后端**（已实查目录确认）。
2. 无运行时支持把同一模型的层拆到 NPU+独显：两套存储（VRAM vs 系统内存）无法共享张量。
3. NPU 带宽 89.6GB/s ≈ 显存的 1/3，算力 11 TOPS，即便跑起来也比 4060 慢。
可行替代：分工——4060 跑 9b 归并，NPU 走 OpenVINO/Windows ML 跑 OCR/embedding 等轻任务（另一条工具链）。
